# Plan 17: Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Settings gets the lab's missing pages — General, Notifications and Shortcuts — and ion starts notifying you the way the lab describes (urgent things notify, things that need you pin, updates wait for a daily briefing), within quiet hours and per-project levels.

**Architecture:** Every setting lives in the user config (`packages/config`), read and written by the daemon (`settings.get` / `settings.set`); the app only displays and edits through the daemon. A daemon `Notifier` turns needs into `notify` events by how loud they are, the project's level and quiet hours, and posts a daily briefing to ion chief's chat (built from views, no model). The desktop shows `notify` events as system notifications through Tauri's notification plugin.

**Tech Stack:** TypeScript, zod config, the daemon's event store and views, React, Tauri 2 (`tauri-plugin-notification`).

**Spec:** the user, 2026-11-19: "also build the settings as well, there are still a ton of settings still not built, please refer to the docs, like the general if needed, tools, notifications, shortcuts and anything else that might be needed". The lab (`docs/design/ion-design-lab.html`): Settings nav General · Agents · Ions · Tools · Notifications · Shortcuts; `renderNotif` (How loud: Urgent → Notify and pin, Needs you → Pin, Updates → Briefing; Timing: Daily briefing 8:30, Quiet hours 22:00–08:00; Per project: All · Needs me · Digest · Muted); the Settings ↔ config table (`notifications.*`, `resources.max_runs`). Tools (Connections, Automations, Skills) is its own plan (Plan 18): it installs MCP servers, hooks and skills into each agent.

## Global Constraints

- Settings nav and order as the lab: General, Agents, Ions, Tools (Plan 18; not shown until then), Notifications, Shortcuts. Icons: `SlidersHorizontal`, `Plug`, `Orbit`, `Blocks`, `Bell`, `Keyboard`.
- Config keys (user config, validated; unknown keys kept): `access.default` ("auto" | "full"), `folders.projects`, `resources.max_runs` ("auto" | 1–32), `debug` (boolean, default false; true lists the test agent like `ION_DEBUG=1`), `notifications.briefing` ({ on: boolean, at: "HH:MM" }, default { on: true, at: "08:30" }), `notifications.quiet` ({ on: boolean, from: "HH:MM", to: "HH:MM" }, default { on: true, from: "22:00", to: "08:00" }), per project `notify` ("all" | "needs" | "digest" | "muted", default "needs").
- How loud (fixed, shown not edited): a blocked call or a failed run that gave up is **Urgent** (notify and pin); an agent's question or anything else in Needs you is **Needs you** (pin); a finished run or thread is an **Update** (briefing).
- Project levels: All = notify for Urgent, Needs you and Updates; Needs me = notify for Urgent and Needs you; Digest = notify for Urgent only, the rest in the briefing; Muted = never notify (still pinned and in the briefing).
- Quiet hours hold every system notification, Urgent included, until they end; then one summary notification ("3 things need you"). Pins and the Needs you list are never held.
- The briefing: one message from ion chief at `briefing.at` on days with something to say: what finished since the last briefing, what needs you, today's routines. Built from views, no model call; plain sentences, no headings.
- The desktop keeps no state of its own (lint); copy rules: short plain words, no hint text, icons named on hover, fewer boxes.
- Appearance is not in this plan: the lab has one (dark) theme. Ruling recorded; a light theme is its own design task.
- `pnpm check && pnpm build`; tour before the PR; no real model calls in tests; lab parity (add General and Shortcuts pages to the lab).

## Review Focus

1. Quiet hours across midnight (22:00–08:00) and same-day (13:00–14:00); a notification at 07:59 is held, at 08:00 goes; the summary goes once.
2. A daemon restart during quiet hours keeps what's held (from events), and the briefing never posts twice for one day (also across a restart).
3. A setting saved with a bad value ("25:00", max_runs 0) is refused with a plain reason and the file isn't touched; a hand-edited config with an unknown key keeps it on save.
4. A project removed or renamed while its notify level is set: no crash, the level goes with it.
5. Many needs at once (ten blocked calls in a minute) make one notification per need when allowed, or one summary when held — never a flood after quiet hours.
