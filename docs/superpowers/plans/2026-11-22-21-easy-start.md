# Plan 21: Easy Start Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** someone who has never used ion gets a useful result in their first few minutes without reading anything:
- open the app;
- see which agents are ready;
- pick a folder;
- send a message;
- watch it work;
- see ion remember something.

Everything else stays out of the way until it's needed.

**Architecture:**
- **First, measure what a beginner meets today.** Use a brand-new ion home on a clean account, and record every screen, word and wait. The fixes come from that record, not from guesses.
- **Then the fixes:**
  - a first-run path in the app and the CLI;
  - one plain vocabulary across both;
  - advanced features shown only when they matter;
  - the live evals run on a schedule, so a broken agent shows up the day it breaks.

**Tech Stack:** React (the desktop app), the CLI, the daemon's existing readiness checks (`apps/daemon/src/ions/brain.ts` isReady, the adapters' sign-in probes), `scripts/tour.sh`, and the live evals in `apps/daemon/src/evals`.

**Spec:** the user, 2026-11-22. In answer to "what do you think of the overall product", I raised the risks: breadth before depth, four words for related things, and no first ten minutes that obviously pays off. I suggested a first-run path, a naming test, a pruning pass and scheduled evals. The user replied: "sure, if that makes the product even easier to use even for beginners". Standing rules: verify, don't guess, and check end to end before calling anything done (2026-11-22); save Claude quota; copy uses short plain words.

## Global Constraints

- **The test is a beginner.** Every change has to make the first ten minutes shorter or clearer for someone new. A change that only helps an expert belongs in another plan.
- **Measure before and after.** On a fresh ion home, measure the time and the number of clicks or commands from opening ion to the first finished answer. Record both in `docs/research/first-run.md`.
- **Nothing is removed without the user.** Pruning means hiding until needed (progressive disclosure). Deleting a feature is a question for the user, listed in the PR.
- **One word per idea, the same in the app, the CLI and the docs.** Renames change the CLI help golden on purpose. Old CLI words keep working as aliases for one release.
- **No new setup steps.** ion must work with zero settings when at least one agent is installed and signed in.
- **Nothing is sent anywhere.** There's no telemetry. "Which features get used" is read from your own local events, only to inform the pruning list.
- The usual rules also apply: copy rules, lab parity, code health, tests first, no real model calls in tests, and a tour before the PR at 1440×900 and 900×700.

## Review Focus

1. **No agent installed or signed in:** the first screen says exactly what to do for each agent in one line, and offers to check again. It never shows an empty chat box that silently fails.
2. **Only opencode's free model, with its quota out:** the first message must not fail with a bare error. ion says so and suggests the next agent to set up.
3. **An existing user upgrading:** they never see the first-run screens again, and none of their projects, chats or settings move.
4. **A folder that isn't a git repo, or a home-folder-sized folder:** the first-run "pick a folder" either works (ion's git setup) or says plainly why not. It never hangs indexing a huge folder.
5. **A renamed word in an old command, note or doc:** the old CLI word still works, and every screen uses the new word. There's no screen left with the old word.

### Task 1: What a beginner meets today

**Files:** `docs/research/first-run.md` (new). No product code.

- **Start a brand-new ion** (temp ION_HOME, an empty projects folder, the app at 1440×900). Go from opening it to a first finished answer with opencode, then Grok, then with no agent signed in. Record each screen (screenshots under `.playwright-mcp/`), every word a newcomer wouldn't know, every wait with no sign of progress, and every dead end.
- **Do the same in the CLI:** `ion`, `ion --help`, `ion status`, the first chat.
- **List every concept word** in the UI, the CLI and the docs: chat, thread, run, ion, ion chief, project ion, harness, agent, routine, need, decision, suggestion, Dream, access, gate. For each, where it shows and what it means.
- **Read the user's local events** for which screens and commands get used. This stays local, and only counts go in the doc.
- **The doc ends with a numbered list of findings,** worst first, each with its screenshot. Tasks 2–4 fix them.
- [ ] Measure → write the doc → commit `docs: what a beginner meets in ion today`.

### Task 2: The first run

**Files:** `apps/desktop/src/start/` (new: the first-run screen), `apps/desktop/src/App.tsx`, `apps/daemon/src/api` (one `start.status` call: agents with ready / not installed / not signed in and the one-line fix, projects count, chats count), the CLI's bare `ion` with no projects, the lab.

- **ion shows the first-run screen** only when there are no projects and no chats. It has three steps on one screen, with no wizard pages:
  1. **"Your agents":** one row per agent:
     - ready;
     - "Install: <command>";
     - "Sign in: <command>" (copyable);
     - plus a Check again icon.
  2. **"Pick a folder":** the folder picker. A non-git folder gets ion's git setup, saying so in one line.
  3. **A message box,** with three example first messages for that folder, for example "What does this project do?", "Find a small bug and fix it" and "Add a test for …".
- **After the first answer,** one quiet line points to what ion now remembers, linking to Settings → Memory. Nothing more.
- **Empty states everywhere else say what to do in one line,** with an action. There are no empty boxes.
- **Bare `ion` in the CLI with nothing set up** prints the same three steps as commands.
- [ ] Tests:
  - "first run shows only with no projects and no chats";
  - "an agent that isn't signed in shows its sign-in command";
  - "no ready agent: the message box waits with what to do";
  - "picking a non-git folder sets up git and says so";
  - "an existing user never sees it".
- [ ] FAIL → implement → PASS → live: a fresh home, from opening ion to a first answer on opencode and on Grok. Time it and compare with Task 1 → commit `feat: a first run that gets a beginner to a first answer`.

### Task 3: One word per idea

**Files:** from Task 1's word list: the desktop copy, the CLI copy and help (golden on purpose), `docs/`, the lab.

- **Settle the vocabulary from Task 1's findings.** The likely outcome:
  - "chat" for any conversation with an agent, including what an ion starts (no "thread" or "run" on screen);
  - "agent" (never "harness" on screen);
  - "ion" for ion chief, with project ions as "<project> ion".
- **List the final table in the PR for the user to confirm before merge.**
- **Old CLI words stay as hidden aliases.** Tooltips, never hint text, explain only the words that remain unfamiliar.
- [ ] Tests:
  - "no screen shows a retired word" (a copy scan over the desktop's rendered strings and the CLI's output);
  - "old CLI words still work".
- [ ] FAIL → implement → PASS → tour → commit `feat: one plain word for each idea, in the app and the CLI`.

### Task 4: Show advanced things when they matter

**Files:** the Settings sections, the rail, the composer menus, the lab.

- **Defaults that work, with the advanced parts tucked away.** Routines, Dream, hooks, tools, access rules and the judge sit under each section's "More", or appear once used. For example, the Routines screen shows once you've made one or an ion suggests one.
- **The Settings sidebar** shows General, Agents and Memory first. Everything else sits under one "More" group until used.
- **A pruning list goes in the PR:** each feature with its local use count and my recommendation (keep / tuck away / ask about removing). Nothing is deleted.
- [ ] Tests:
  - "advanced sections stay tucked away until used";
  - "a used section stays shown";
  - "nothing becomes unreachable": every screen can still be reached from Search and the CLI.
- [ ] FAIL → implement → PASS → tour (beginner and existing user) → commit `feat: advanced settings appear when they matter`.

### Task 5: Live evals on a schedule

**Files:** `scripts/evals-nightly.sh` (new), plus a built-in ion routine "Check the agents" (off by default, offered once in Settings → Agents), and `docs/research/acp-and-harnesses.md`.

- **The routine runs each night** when the machine is awake and idle:
  - the live evals for each signed-in free or subscription agent (opencode, Grok, Codex);
  - Claude only if you turn it on.
- **The results** land in `.ion-evals/` and as one line in Settings → Agents: "Checked last night: all fine", or "Grok: 2 checks failed", which opens the details. A failure becomes a "needs you" note only the first time.
- **It never runs during the working day,** and skips an agent marked limited.
- [ ] Tests:
  - "the routine skips a limited agent";
  - "a failure notifies once";
  - "off by default".
- [ ] FAIL → implement → PASS → live: run it once by hand on opencode and Grok → commit `feat: ion checks its agents nightly and tells you if one broke`.

### Task 6: Verify as a beginner, end to end

- **`scripts/tour.sh` gains a fresh mode,** `tour.sh fresh`: no projects, no chats, for the first-run screen.
- **Live, on a brand-new home,** do the whole beginner path on opencode and Grok. Time it against Task 1's numbers. Then repeat as an existing user (the normal tour) to check nothing moved.
- **Docs:** `docs/README.md`, `AGENTS.md` (the word table), and a "First run" milestone in the walkthrough artifact.
- [ ] Run → fix what fails (each with a failing test first) → commit `test: the beginner path checked end to end`.
