# Plan 18: Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Settings → Tools has three tabs: **Connections** (MCP servers every chat's agent can use, signed in the standard way: OAuth, an API key, or the server's own login), **Hooks** (every ion event, each with the hooks that run on it — ion's own Auto-approval built in, never turned off in Settings), and **Skills** (the skills your agents already have, on or off).

**Architecture:** Tools live in ion's user config; keys and tokens live in the OS keychain, never in config. ion is the OAuth client for remote MCP servers (the MCP authorization spec: protected-resource metadata → authorization-server metadata → dynamic client registration → authorization code with PKCE, redirect to the daemon on localhost) and hands each run a fresh `Authorization` header — agents never see a refresh token. Each run gets your enabled servers the way it already gets ion's own (per run; ion never writes an agent's own config). Hooks run in the daemon's workspace layer on ion's events; "Before a tool runs" hooks can refuse a call, ahead of the built-in Auto-approval. Skills are found where each agent keeps them and passed to Claude Code through the Agent SDK's `plugins: [{ type: "local", path }]` (how T3 Code does it), so ion's settings stay off and its gate still sees every call.

**Tech Stack:** TypeScript, zod config, macOS Keychain (`security`) / Linux Secret Service (`secret-tool`), OAuth 2.1 + PKCE (RFC 9728, 8414, 7591), the adapters' MCP paths (Agent SDK `mcpServers`, Codex `config.mcp_servers`, ACP `session/new` `mcpServers`), React.

## Global Constraints

- **No secrets in config or logs.** API keys and OAuth tokens go in the OS keychain under service `ion`, account `mcp:<id>:<kind>`; config holds only which kind of sign-in a server uses. Never in argv, the event log, the daemon log, or an error message. On a system with no keychain (no `security` / `secret-tool`), signing in is refused plainly ("ion can't store keys on this computer").
- **Sign-in kinds** (MCP authorization spec and common practice): `none`; `oauth` (remote servers that answer 401 with `WWW-Authenticate` / protected-resource metadata: ion discovers, registers itself dynamically if the server allows, else asks for a client ID; authorization code + PKCE (S256); redirect `http://127.0.0.1:<daemon port>/oauth/callback`; state checked; tokens refreshed before expiry; a refresh that fails marks the server "Sign in again"); `apiKey` (a key you paste once, sent as a header you name, default `Authorization: Bearer <key>`, or for a stdio server set as an env variable you name); `own` (a stdio server that handles its own login, e.g. one that uses `gh auth` — ion passes nothing).
- **Connections come from a file** (the user, 2026-11-20: "it is better to import custom mcp through a config file rather than on app, but there should be a way to access the config file"): `$ION_HOME/mcp.json` in the standard `mcpServers` shape Claude Code and Cursor use — stdio `{ "command", "args", "env" }`, remote `{ "type": "http" | "sse", "url", "headers" }`. ion creates it as `{ "mcpServers": {} }` when missing, watches it, and reloads on save; a broken file shows one plain line on the Connections tab and ion keeps the last good one. Values may use `${NAME}`: filled from a key you entered in the app for that name (keychain), else ion's environment. The app does not add or edit servers: it lists them, opens the file (**Open config file**, `FileCog`, via Tauri's opener), signs in, takes a missing key, and turns each on or off (stored in ion's config, never written into mcp.json). OAuth is detected the standard way (the server answers 401 with `WWW-Authenticate`).
- **Consent:** servers are added only by you editing mcp.json; signing in, keys and on/off only from the app; hooks only from the app. Agents can't: ion's config file, data folder and keychain items are out of every run's reach (gate test).
- **Transports:** remote servers over Streamable HTTP (`https`, or `http` only on localhost); local servers over stdio (command + args). Names: 1–40 chars, letters, digits, `-`, `_`; `ion` is reserved.
- **Never write an agent's own config.** Servers and skills reach a run through the adapter, per run, beside ion's own `ion` server. They reach chat runs only, never ion's own turns or the judge.
- **Hooks:** the Hooks tab lists every ion event a person would care about (the catalog in Task 4), with or without hooks. **Auto-approval** is a built-in hook on "Before a tool runs": shown with a "Built in" chip — no remove, no switch, nothing in Settings turns it off. It is turned off only per chat, with the access icon in the composer (the user, 2026-11-20: "auto-approval should not be allowed to be disabled in settings, never settings, only through switching the access icon in composer"). So General's Default access (Plan 17) is removed too: new chats always start with Auto, and `access.default` is no longer read (a hand-edited value is ignored with a warning). A user hook is a command (`/bin/sh -c`), stdin = the event JSON, env `ION_EVENT`, `ION_PROJECT`, `ION_CHAT`, cwd = the event's project folder (else ion's home folder), 60 s limit (10 s for "Before a tool runs"), last 2,000 chars of output kept (shown as the hook's last result), at most one running per hook (one more waits, the rest are dropped). On "Before a tool runs", exit 2 refuses the call with its stderr as the reason (as Claude Code's hooks do); any other result lets it go on to Auto-approval; a hook that times out lets it go on and is reported. Routines stay where they are (Ions); there is no Automations tab.
- **Skills:** found in each agent's own folders (Claude: `~/.claude/skills`, the project's `.claude/skills`; Codex: `~/.codex/skills`; opencode: `~/.config/opencode/skills`, `.opencode/skills`; `.agents/skills`), each a folder with `SKILL.md`; on/off per skill. Claude Code loads the enabled ones through `plugins` (a generated plugin folder in ion's data folder, rebuilt per run); agents ion can't pass skills to show dimmed ("Uses its own").
- Plain words, no hint text, icons named on hover, fewer boxes; lab parity (CSS via copy-lab ranges); child processes only where AGENTS.md allows (add `apps/daemon/src/secrets` to the `ion/no-child-process` allow list for the keychain CLIs, and say so in AGENTS.md).
- `pnpm check && pnpm build`; tour before the PR; no real model calls in tests (OAuth tested against a local fake authorization server); live check on opencode's free model and Grok.

## Review Focus

1. A remote server whose token expires mid-day: the next run gets a refreshed token; if refresh fails, the server shows "Sign in again" and runs go on without it (said once in the chat), never a failed run.
2. A pasted key or a token appearing anywhere it shouldn't: argv of an agent process, the event log, the daemon log, config.toml, an error shown in the app.
3. OAuth done wrong: a callback with the wrong `state`, a redirect to anything but the daemon on 127.0.0.1, an authorization server on plain http (not localhost), a server with no dynamic registration — each refused or asked plainly, no token stored.
4. A "Before a tool runs" hook that hangs, crashes or prints garbage: the call goes on to Auto-approval after 10 s, the chat isn't stuck, the hook is reported once.
5. An agent asked to add a server, sign in, read a key, or add a hook: it can't.
