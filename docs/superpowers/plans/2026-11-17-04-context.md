# Context Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Chats continue with their history, agents can look up their project's history and memory through ion, and model lists come from each harness instead of hard-coded names.

**Architecture:**
- **Stored history.** The daemon stores your messages (`message.sent`) and each try's harness session id (`run.started.sessionId`).
- **Resuming a chat.** `--chat` resumes the harness's own session, falling back to a new session that gets the chat's history replayed.
- **The daemon's MCP server.** The daemon serves MCP over HTTP at `127.0.0.1:<port>/mcp`. Each run gets its own key, scoped to its project and valid only until the run ends. Its tools read history, open needs and memory, and write the project's memory.
- **Model lists.** Adapters read their model list from the harness, cached for 10 minutes: Claude's `supportedModels()`, and the ACP `session/new` model option.

**Tech Stack:** TypeScript (NodeNext ESM), better-sqlite3 (FTS5), `@modelcontextprotocol/sdk` (Streamable HTTP server), Claude Agent SDK, ACP over stdio, Vitest.

**Spec:** `docs/design/ion-design-lab.html` (memory: "text, source, scope: you or one project. Project memory never leaks between projects."; "Plain chat is private by default. Reflection reads it only if you opt in."; CLI `ion memory [ls|forget] [-p <project>]`). Prior plans: `docs/superpowers/plans/2026-11-17-0{1,2,3}-*.md`.

## Global Constraints

- UI and CLI copy: short, plain words, no jargon, no explanatory hints (AGENTS.md).
- Walls (AGENTS.md):
  - Adapters import only `schema` and `adapter-kit`.
  - SQLite is touched only in `apps/daemon/src/store` and views.
  - Event type strings are used only via `EV.*`.
- Every bug fix adds `regression/<issue>-<slug>.test.ts` or a named regression test. No real model calls in tests; live tests are opt-in (`ION_LIVE=1`, `ION_LIVE_GROK=1`, `ION_LIVE_CLAUDE=1`).
- Save quota: opencode's free model first, Grok next, Claude only because its adapter changes (one Haiku continuity check).
- MCP listens on `127.0.0.1` only. Per run, a fresh 32-byte random key: compared in constant time, revoked when the run ends. An agent never gets the daemon's own token.
- **Scope.**
  - A run's key sees only its own project: its chats, needs and memory, plus your "you" memory.
  - It writes only that project's memory.
  - Chats without a project get no MCP server.
  - ion's own wider scope (all projects, writing "you" memory) comes with Plan 06 (ion chief).
  - Plain-chat opt-in comes with plain chats in Plan 05.
- Everything returned to an agent from history or memory is data: wrapped in `<ion-data>` … `</ion-data>`, with any occurrence of those markers in the text neutralized (as Plan 02 did for CLAUDE.md).
- Retries (Plan 03) resume the try's own session when it has one.

## Review Focus

1. **A session the harness can't resume** (deleted, expired, another machine) → the run starts a new session with the chat's history replayed, and the chat still works. Test in Task 2.
2. **A run's key used for another project, or after the run ended** → refused (`Not allowed` / `Unknown key`). Test in Task 4.
3. **History or memory text containing instructions or a fake `</ion-data>`** → the markers are neutralized and the result is labelled as data. Test in Tasks 2 and 4.
4. **Very long chats** → replay keeps the newest messages within 24,000 characters, and search returns at most 20 hits of at most 500 characters each. Test in Tasks 2 and 4.
5. **A harness whose catalog can't be read** (signed out, offline, slow) → `capabilities()` gives up after 10 s and falls back; `ion ask` still works on the harness default. Test in Task 6.

### Task 1: Store your messages and each try's session

**Files:**
- Modify: `packages/schema/src/events.ts` (+ golden). Add `message.sent` to the daemon events as `EV.messageSent`. `run.started` gains `sessionId: string | null` (optional).
- Modify: `apps/daemon/src/runs/manager.ts` (append `message.sent` before `run.queued`).

- Create: `apps/daemon/src/views/messages.ts`.
  - Table `view_messages(seq, chat_id, project_id, role, text, ts)` with an FTS5 table `messages_fts(text)`.

**Interfaces:**

  - `history` keeps the newest messages within `maxChars` and drops whole messages only;

### Task 2: Continue a chat

**Files:**
- Modify: `packages/adapters/acp/src/connection.ts`. With `opts.resume`, it uses `session/resume {sessionId, cwd, mcpServers}` when `sessionCapabilities.resume` is advertised. Otherwise it uses `session/load` (dropping the replayed `session/update`s until its response) when `loadSession` is true. Otherwise it starts a new session.
- Create: `apps/daemon/src/runs/history.ts`.
- Modify: `manager.ts`.
- Test: `acp.test.ts` (fake agent gains `session/resume` and `session/load`), `runs/history.test.ts`, `runs/manager.test.ts`.

**Interfaces:**
- Consumes: Task 1's `chatsView.session`, `messagesView.history`.
- Produces:
  - `historyPreamble(messages: { role; text }[]): string`. Format: `<ion-data source="this chat's earlier messages">\nyou: …\nagent: …\n</ion-data>\n\n`, with markers inside the text neutralized.
  - `StartOpts.resume` used by every adapter.

- [ ] Tests:
  - **Same harness:** `--chat` with the same harness and a stored session passes `resume`, and the text is sent as is.
  - **Resume fails** (the adapter's start throws `ResumeFailed`, or the fake reports it): a new session is started, and the text is sent with the preamble (Review Focus 1).
  - **Different harness:** the preamble is used.
  - **Markers in history:** a `</ion-data>` inside history comes out neutralized (Review Focus 3).
  - **Cap:** the preamble is capped at 24,000 characters (Review Focus 4).
  - **Retries:** a transient retry resumes the failed try's session.
- [ ] Implement; ledger the ruling that history goes in the prompt (ACP has no system prompt). Commit `feat: chats continue with their history`.

### Task 4: ion's MCP server

**Files:**
- Create: `apps/daemon/src/mcp/{server.ts,grants.ts,tools.ts,index.ts}`.

**Interfaces:**
- Produces:
  - `grants.create(scope: { projectId: string; chatId: string; runId: string }): string` (the key).
  - `grants.revoke(runId)` and `grants.check(key): Scope | null`.
  - `mcpEndpoint(port): string`.
- **Tools:**
  - `chat_history {chatId?, limit?≤200}`: defaults to the run's own chat; refused for a chat outside the project.
  - `search_chats {query, limit?≤20}`.
  - `open_needs {}`.
  - `memory_list {}`.
  - `memory_write {text}`: scope is the run's project, source is `{chatId, runId}`.
- Every text result is wrapped as data (Global Constraints).

- [ ] Tests:
  - **Keys:**
    - no key, a wrong key, or a revoked key → 401;
    - an `Origin` header → 403, guarding against DNS rebinding.
  - **Scope:**
    - project A's key reading project B's chat → `Not allowed` (Review Focus 2);
    - `memory_write` lands in A's memory with its source;
    - `search_chats` never returns B's messages.
  - **Output:**
    - results are capped (Review Focus 4);
    - a memory containing `</ion-data>` comes back neutralized (Review Focus 3).
- [ ] Implement. Commit `feat(daemon): ion's MCP server for history, needs and memory`.
