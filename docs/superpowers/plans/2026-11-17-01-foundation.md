# ion Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A running ion daemon with an append-only event log, file-based config, a typed WebSocket API, and an `ion` CLI that talks to it, guarded by architecture walls, custom lint rules and CI.

**Architecture:** pnpm + Turborepo monorepo. `packages/schema` is the contract (event envelope, types, validators). `apps/daemon` owns all state: `store/` is the only SQLite writer, `views/` are tables updated as each event is appended. `packages/client` is the typed WebSocket client that both the CLI (now) and the desktop app (Plan 4) use.

**Tech Stack:** TypeScript 5.9 (strict, ESM), Node ≥ 24, pnpm 10, Turborepo 2, Vitest 3, Biome 2 (format), ESLint 9 + typescript-eslint + eslint-plugin-boundaries (walls, custom rules), zod 4, ulid, better-sqlite3 + drizzle-orm, ws, commander, smol-toml.

**Spec:** `docs/design/ion-design-lab.html` (Architecture, Engineering and CLI sections) and `docs/architecture/contract.md`.

## Roadmap (one plan each, each ships working software)

1. **Foundation** (this plan)
2. Adapter kit, fake harness, Claude Code adapter: `ion ask` runs a real coding turn headless
3. Workspace (worktrees, dev servers), scheduler and resource queue, policy and approvals, needs, retries
4. Desktop app: Tauri 2 + React, design system, Chats screens, thinking/tool umbrella
5. ion chief: Quick/Deep models, routing, fan-out, briefing; Ions screens
6. Routines, Activity, Artifacts store and checks hook, Tools (MCP, automations, skills)
7. Suggestions and memory
8. More adapters: Codex, Grok Build, Gemini CLI, Cursor CLI, Pi

## Global Constraints

- License Apache-2.0. macOS and Linux supported; Windows later.
- Node `>=24`, ESM only (`"type": "module"`), TypeScript `strict: true`, `noUncheckedIndexedAccess: true`.
- Package scope `@ion/`. Packages: `schema`, `config`, `client`; apps: `daemon`, `cli`.
- Config file: `$XDG_CONFIG_HOME/ion/config.toml` (default `~/.config/ion/config.toml`). Data dir: `$XDG_DATA_HOME/ion` (default `~/.local/share/ion`). `ION_HOME` overrides both (config at `$ION_HOME/config.toml`, data at `$ION_HOME/data`); every test uses a temp `ION_HOME`.
- Daemon listens on `127.0.0.1` only, random free port, writes `daemon.json` `{ pid, port, token }` to the data dir with mode `0600`. Every WS connection must send the token; otherwise close with code `4401`.
- Only `apps/daemon/src/store/` may import `better-sqlite3` or `drizzle-orm`.
- Event type strings exist only in `packages/schema`; everywhere else imports the constants.
- No real model calls anywhere in this plan's tests.
- CLI: human output by default, `--json` for machine output, exit code `0` ok, `1` error, `2` daemon not running.
- UI copy rule (applies to CLI output too): short, plain words, no jargon, no explanatory hints.

## Review Focus

1. **Starting the daemon twice** → second `ion daemon start` prints "Already running" and exits 0; never two daemons on one data dir (lock via `daemon.json` pid check). Test in Task 6.
2. **Stale `daemon.json`** after a crash (pid no longer alive) → `start` replaces it; `status` reports not running. Test in Task 6.
3. **Concurrent appends to two runs** → each run's `seq` is gapless from 1; appending an event with an existing `id` is a no-op returning the stored event. Test in Task 3.
4. **Malformed or old config file** → a clear one-line error naming the file and the key; the daemon still starts with defaults rather than crashing. Test in Task 4.
5. **`ion projects add` on a path that doesn't exist or isn't a git repo** → error "Not a git repository: <path>", exit 1, config unchanged. Test in Task 4.
