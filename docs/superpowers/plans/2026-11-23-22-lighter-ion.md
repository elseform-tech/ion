# Plan 22: Lighter ion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ion spends fewer tokens and less time on its own work (the judge, ions, Dream, the briefing, readiness checks), with no loss in safety, recall or what you see. Each cut comes from a measurement and is guarded by the evals.

**Architecture:**
- **Measure first.** Plan 20's usage ledger already records ion's own calls per agent. This plan splits that by purpose (judge, ions, Dream, briefing, chats) and shows it in one line.
- **Cut only what the numbers show is big.** Each candidate cut runs behind the existing evals before and after:
  - the judge evals (`apps/daemon/src/evals/judge-*`);
  - the memory and Dream evals (`apps/daemon/src/evals/memory*`);
  - the live checks.

**Tech Stack:** TypeScript, the usage view (`apps/daemon/src/views/usage.ts`), the judge (`apps/daemon/src/access`), ions (`apps/daemon/src/ions`), the scheduler, `HarnessInfos` (readiness).

**Spec:** the user, 2026-11-23: "do you think there are any bloats we can remove or consolidate to have better performance or help save more token costs, without compromising". I proposed: measure first, then cut where it's big, each change guarded by the evals. The user said "sure". Standing rules:
- verify, don't guess, and check end to end before calling anything done;
- save Claude quota;
- you own your own work (no limits or nags on your chats).

## Global Constraints

- **No compromise is the bar.** Every cut must keep these at their current values on Grok and opencode:
  - the judge eval's agreement, with 0 unsafe allows;
  - the memory eval's recall and privacy: 0 leaked, 0 orders obeyed;
  - the Dream eval: 0 valid facts broken.

  Record before and after in `docs/research/lighter-ion.md`. A cut that lowers any of them is dropped.
- **Your own chats are untouched.** This plan changes only ion's own overhead and readiness checks, never what your chats send or how agents work.
- **Measured, not estimated.** Every number in the doc comes from the usage ledger or a timed run, with how it was measured. "Saves about X" is never written without a before/after measurement.
- **Nothing is sent anywhere.** Measurement stays local.
- The usual rules: copy rules, lab parity, code health, tests first, no real model calls in tests, a tour before the PR.

## Review Focus

1. **A cached readiness answer that's stale:** an agent signed out since the last check. A run on it fails with a clear sign-in reason and refreshes the cache. It never hangs, and the agent is never shown as ready for long after a failure.
2. **A reused judge answer applied where it shouldn't be:** the same command text in another chat, project or worktree, or after you changed an access rule. Reuse is keyed on the exact action, chat and rules version, and never crosses chats.
3. **An ion's fresh session losing what it needs:** an open question, a pending to-do or a thread it started. The summary carries these, and the ion evals still pass.
4. **Skipping Dream or the briefing on a "nothing new" day** when something did change, for example a file you edited by hand. "Nothing new" is decided from events and file changes, not guessed.
5. **The overhead line misattributing usage:** a chat's run counted as ion's own, or the reverse. Each usage event carries its purpose from where it started.

### Task 2: Readiness without waiting

**Files:** `apps/daemon/src/adapters` (`HarnessInfos`), and the callers that wait on readiness: the limit question, `ion status`, the composer, and ion fallback.

- **Cache each agent's last readiness answer, and refresh it in the background:**
  - on start;
  - every few minutes while ion is in use;
  - right after a run on that agent fails with a sign-in or install reason.
- **Callers read the cache at once.** They never wait on a CLI check, except at the very first start, bounded as today.
- [ ] Tests:
  - "the limit question offers agents without waiting on a check";
  - "a sign-in failure refreshes that agent's answer";
  - "a stale ready answer fails with a clear sign-in reason, not a hang".
- [ ] FAIL → implement → PASS → live: time `ion status` and the limit question, cold and warm, before and after → commit `perf: ion knows which agents are ready without waiting`.

### Task 4: Ions, Dream and the briefing, lighter

Only for the parts Task 1 shows are large.

**Files:** `apps/daemon/src/ions` (sessions), `apps/daemon/src/memory/dream.ts`, the briefing.

- **An ion's session starts fresh with a summary once its history passes a budget,** using the Plan 20 brief pattern. The summary carries:
  - open questions;
  - to-dos due;
  - threads in flight;
  - the last decisions.
- **Dream skips a period with nothing new:** no memory written, no file edited and no chat in that scope since the last run. "Nothing new" is decided from events and file changes.
- **The briefing skips a model call** when there's nothing to say, and shows the plain list instead.
- [ ] Tests:
  - "a long ion session starts fresh with what it needs";
  - "Dream skips a scope with nothing new and runs when a file changed";
  - "the briefing without news makes no model call".
- [ ] FAIL → implement → PASS → memory, Dream and ion evals before/after (no drop) → commit `perf: ions, Dream and the briefing do only the work there is`.
