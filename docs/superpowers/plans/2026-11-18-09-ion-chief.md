# ion chief and the Ions screen Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every project gets its own ion. ion chief sits over them all. You can message any ion from a new Ions screen. In threads an ion started, agents' questions reach the project's ion first.

**Architecture:**
- **Ion chats.** An ion's chat is an ordinary event stream under the pseudo chat id `ion:<ionId>` (`ion:chief`, `ion:storefront`). The client's existing `subscribe({ chatId })` shows it with no new plumbing.
- **Project ions start threads.** Messaging a project's ion starts a *thread*: a normal chat in that project, marked `by: "ion"`. The ion then reports back in its own chat.
- **ion chief routes.** ion chief classifies each message on a quick model, ion's "System 1": the `[ion] brain` harness, run bare like the judge. It either answers from what the daemon's views already know, or routes the message to one or more project ions.
- **Questions in ion threads.** These go through the project's ion first. It answers from any of your decisions in that project, holds duplicates of a question already waiting, and otherwise passes the question to you with a note. It also suggests "always" decisions and flags decisions that keep failing.

**Tech Stack:** TypeScript, Node daemon (SQLite views, MCP), React desktop (Tauri 2), Vitest.

## Global Constraints

- AGENTS.md walls and code health hold:
  - event type strings only in `packages/schema` (`EV.*`);
  - SQLite only in `apps/daemon/src/store`;
  - model names only in adapters;
  - adapters load only in `registry.ts`;
  - 80 lines per function, 15 complexity;
  - the health ratchet must not get worse.
- **Plain chats are never ion's.** Chats you drive yourself (any chat not `by: "ion"`) never get ion routing, ion answers or ion notes. This is the user's decision of 2026-11-18.
- **`default` has no ion** (ruling, for review). It pools every chat without a project, so it gets no row in Ions, no threads, and no routing. ion chief can still say what's happening in it.
- **ion never edits code.** ion chief only answers and routes. A project ion only starts threads; the thread's agent does the work.
- **ion's own model** (System 1) is `[ion] brain = "<harness>:<model>"`, defaulting to `[access] judge`. It runs bare, like the judge (`harnessRunner`), and spends a harness's own login, never an API key.
- **No real model calls in tests.** Use the fake harness's scenarios, or an injected runner.
- **UI rules:**
  - a quiet chat, with no hint text;
  - icons over words, named on hover;
  - fewer boxes;
  - no one-side coloured stripes.
- **Avatars:** in the sidebar, an avatar in a row's first slot means a thread ion started; your chats keep it empty. A project ion's avatar is its harness's shape in the project's colour (the lab's `hybrid`). ion chief is the lab's ink circle with its orbit ring.
- **Ion colours** come from the lab's `PAL`, in this order: Orange `#ED712E`, Green `#5BC67A`, Amber `#F19D38`, Blue `#3C82F6`, Purple `#885CF5`, Teal `#54B9A6`, Pink `#EB4699`, Red `#EA4045`, Brown `#97683D`. Colours are identity only, never status.
- **Every UI task ends with the tour** (`scripts/tour.sh`, per AGENTS.md). Extend the tour script with an ion thread and a message to ion chief.
- **Copy:** placeholder "Message <name>"; ion chief's name is shown as the wordmark "ion"; the left panel title is "ions".

## Left out (later plans)

- **Plan 10:** routines, Activity, the daily briefing, Artifacts, Tools.
- **Plan 11:** suggestions from signals, and the awake and asleep states.
- **Also later:** ion settings (brain, colour, harness per ion), adding a project from the app (it needs a folder picker), starring ions, and searching.

## Review Focus

1. **A question in your own chat that looks like one in an ion thread.** It still comes to you unchanged: no ion note, no ion answer. Test in Task 4.
2. **ion chief's model is down or slow, or answers with junk.** Your message still gets a reply, "I couldn't reach my model; try again", and nothing is routed. Test in Task 3.
3. **Two ion threads ask the same question.** Only one reaches you, and your answer settles both. If the first is answered elsewhere (the CLI) or its run stops, the held one is raised to you, never lost. Test in Task 4.
4. **Routing to a project ion whose harness isn't ready** (signed out). The thread isn't started, and ion chief says which project it couldn't reach. Test in Task 3.
5. **Agent text in ion cards** (thread titles, previews, notes) is text, never HTML, and the CLI strips control characters with `stripControl`. Test in Task 6.

**Interfaces:**
- **Consumes:**

  - `harnessRunner(configFile)`, with a `spec` argument for `[ion] brain`;
  - `wrapData` for prompts.
- **Produces:** `class Ions { message(ionId: string, text: string): Promise<void> }`.
  - It always appends `ion.heard` first.
  - **A project ion:** `runs.ask({ projectId: ionId, text, harness: project.harness, by: "ion" })`, then `ion.said` "On it." with card `threads` `[{chatId, projectId}]`.

    - **`route`:** for each project, the same path as a project ion (`ion.heard` with the brief on that ion's chat, then a thread). ion chief then says "Asked N projects" with one `threads` card listing all of them.

    - A failed, slow or unparseable model answer gives `ion.said` "I couldn't reach my model; try again", and routes nothing (Review Focus 2).
  - **When an ion thread's run ends,** its ion says one line: "<title>: done" or "<title>: failed", plus the start of the reply (`ChatInfo.preview`), with card `threads` `[that chat]`.
  - `parseRoute(text, projects): Route | null` accepts only JSON naming known projects other than `default`.

### Task 4: Questions in ion threads reach the project's ion first

**Files:**
- Modify: `apps/daemon/src/decisions/service.ts` (and `match.ts` if its prompt needs the scope), `apps/daemon/src/needs/service.ts`, `apps/daemon/src/views/needs.ts` (held needs aren't open)
- Create: `apps/daemon/src/ions/questions.ts` (+ test)

**Interfaces:**
- **Consumes:** `Decisions.ask`, `fromPast`, `record`, `answer`; the matcher; `ChatInfo.by`; `ion.said`.
- **Produces:** in `Decisions.ask`, when the asking chat is `by: "ion"`:
  1. **Answer from the project's decisions.** The matcher runs over *every* decision you made in that project (chat, project or everywhere scope; `by: "you"`, not only "always"). A match answers as ion does today ("Answered by ion from your decision on <date>"), and the ion says so in its chat.
  2. **Hold a duplicate.** If an open question in the same project's ion threads matches this one (the same matcher, run against the open question as a past decision), the new need is raised with `heldFor: <open needId>`. It isn't shown as open.
     - When the open one is answered, each held one is answered from that new decision.
     - If the open one is closed any other way (superseded, its run stopped), each held one is raised normally (Review Focus 3).
  3. **Otherwise,** raise it to you with `via.note`: the ion's one line of context. For example, "storefront's ion: you answered a similar question 'Use QA account' on 18 Nov", or "storefront's ion: first time this comes up".
  4. **Suggest "always".** After you answer, if you've given the same choice to matching questions 3 times in this project, the ion says a `suggest` card. Keep records a project-scope decision; No records nothing, and the same suggestion isn't made again for that question.
  5. **Flag failing decisions.** When a decision gets its second `failed` outcome, the ion says a `flag` card ("<choice> for '<question>' led to 2 failed runs").
  - **A chat not `by: "ion"` is unchanged** (Review Focus 1).
