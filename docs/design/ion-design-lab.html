tssrc/cart/money.ts
export const toCents = (n: number) =>
  Math.round(n * 100);

export const fromCents = (c: number): Money =>
  ({ cents: c, amount: c / 100 });

export function discountCents(c: number, d: Discount) {
  return d.kind === "pct"
    ? Math.round((c * d.value) / 100)
    : Math.min(c, toCents(d.value));
}

export function sumLines(lines: Line[]) {
  return lines.reduce(
    (s, l) => s + toCents(l.price) * l.qty, 0);
}

Projects and routines

Every project gets exactly one ion. You never “create an ion”: you add a project, then give its ion routines.

Add a projectits ion comes with it
  1. 1Press + in IonsOr tell ion “add ~/code/billing-v2”.
  2. 2Pick the folderThe name comes from the folder. Brain and color have defaults; change them if you like.
  3. 3Its ion reads the repoStack, scripts, tests and CI, then it offers to suggest routines.
Add a routineby asking
  1. 1Ask ion or the project’s ion“Every Monday, update storefront’s dependencies.”
  2. 2A routine card appearsTrigger, harness, effort and instructions, picked for you. Keep, Change or Undo.
  3. 3It runs on scheduleUpcoming runs show in Activity; anything that needs you is pinned.
  4. 4Same job elsewhere?“Do the same on payments-api” copies the routine. Each project keeps its own memory.

Data model

Project = one ion (brain, color, memory) → Routine (instructions, trigger, harness, effort). Chat → Run → Event. Need (pin, state, evidence). Artifact (versioned blob, from the agent or a hook). Tool (MCP server or hook). Usage. Signal (from a project ion or a rule) → Proposal (evidence, action, cost, state). Memory fact (text, source, scope: you or one project). Project memory never leaks between projects.

What BYO means

Connect is one click: ion runs each CLI’s own login, and the CLI handles whether that’s a subscription or an API key. ion never sees credentials or bills for models. ion’s own thinking uses a connected harness too, so it shows in that harness’s quota. Each provider’s terms for automated use still need checking.

Hard parts

  • Approvals work differently in every harness. Mapping them all to one pin model is the core of the adapters.
  • Adapters break when the CLIs change. As an open-source project, version them and give each its own tests.
  • Runaway cost: handoff limit, per-role caps, quota-aware routing.
  • Concurrency: a run queue with limits, so ten roles don’t mean ten heavy processes at once.
  • Secrets: scoped to each worktree, redacted from evidence.
  • Useful, not naggy: a daily cap, expiry, learning from dismissals, and evals that score whether a proposal was worth showing.

Decided

  • Views update as events arrive: SQLite tables, with snapshots for fast starts.
  • Config stays in files; work, needs and routines are events.
  • Retries: exponential backoff with full jitter for transient errors; one higher-effort retry for real failures.
  • ion thinks in two systems: System 1 with thinking off, System 2 with an effort level. You pick both and when System 2 is used.
  • No proof runner: Playwright via MCP, plus a built-in checks hook. All output goes to the Artifacts store.
  • Only ion is proactive. Project ions send signals; ion reflects on System 2 within a budget and proposes. Suggestions never count as needs.
  • Plain chat is private by default. Reflection reads it only if you opt in.
  • Plugins, v1: MCP servers and ion hooks only. Skills where the harness supports them. No marketplace until people ask.

Cloud runners, later

A cloud runner runs the same daemon, with the scheduler able to send runs to it. Because everything goes through the event log, the app can’t tell where a run happened. Turning them on later doesn’t touch the UI, roles or pins.

Custom lint rules each locks in a decision

no-need-events-outside-daemonProject ions never notify you directly. Only daemon/needs creates need.*, route.*, claim.*.
no-direct-db-writesOnly store/ touches SQLite; everything else appends events.
event-types-from-schemaEvent names come from schema, never string literals.
no-child-processOnly workspace/ and adapters spawn processes, so sandbox and concurrency limits hold.
no-network-in-uiThe desktop talks only through client; the UI only displays.
no-model-names-outside-adaptersModel lists come from capabilities().
no-raw-colorsTokens only; status colors only through <Status>.
artifacts-through-redactorNothing reaches the Artifacts store without redact().
no-credential-accessOnly an adapter’s auth.status() may look at CLI login folders.
one-ion-per-projectA project ion is keyed by its projectId; nothing can create a second one.
no-inline-promptsPrompt text lives only in packages/prompts, with an id and version. No prompt strings in code.
config-through-loaderNo process.env or config-file reads outside packages/config, so precedence can’t be bypassed.
cli-through-clientThe CLI uses the same client as the app. No back door into the daemon.

Fixed bugs can’t come back. A PR labeled bug fails CI unless it adds or changes a test or lint rule, named after the issue (regression/#412-duplicate-pins.test.ts). Fuzzer crashes are minimized into fixtures/fuzz-corpus and replayed on every PR.

What we test

Tests

  • Unit: policy, schema, needs. Coverage floors per package, e.g. policy ≥ 95%
  • Adapter contract suite + recorded-transcript replays
  • Fake harness: full end-to-end with no model calls
  • Event log: replay gives the same state; old versions load; crash resume
  • Sandbox escapes must fail
  • Visual regression on the design system and key screens

Fuzzing

  • Adapter parsers: broken JSON, unknown events, huge payloads
  • Policy: ../, symlinks, Unicode, shell tricks
  • Redactor: no generated secret ever leaks
  • Agent output in the UI: no script ever runs
  • Event log as a state machine: a need resolves exactly once
  • WebSocket frames; branch names from chat titles

Load and stress

  • 20 projects × 10 roles, 50 runs queued, limit 6
  • 10 runs × 200 events/s: UI p99 < 100 ms
  • 1M-event log: replay < 10 s, cold start < 2 s
  • 5k chats, 10k Library items at 60 fps
  • 24 h soak: flat memory, idle < 150 MB
  • Chaos: kill daemon or adapter, hung CLI, disk full

Complexity

  • Count operations, not time: 10× input ≲ 15× work
  • Database query counts per request (no N+1)
  • Hot queries must use an index (no full scan of events)
  • Rendered elements stay flat: lists are virtualized
  • Hash-based dedupe, indexed pin lookup, linear replay

Evals ion’s judgment

  • Fan-out to the right projects ≥ 90%
  • Triage: no missed interrupts
  • Dedupe: one outage → one pin
  • Unproven claims caught ≥ 95%
  • Briefings: 0 invented facts
  • Tracked by model; regressions block release

Prompts

  • Snapshot of each rendered prompt with fixture data
  • Token budget per prompt (e.g. triage < 2k)
  • Injection: agent output inside a prompt can’t escape its delimiters (fuzzed)
  • Changed prompt → its evals run before merge (capped)
  • Every prompt version recorded with the events it produced

CLI

  • Snapshots of help text and human output
  • --json output validated against schema
  • Exit codes: 0 ok · 1 error · 2 usage · 3 needs you
  • Non-TTY, piping, NO_COLOR, no prompts in CI mode
  • End to end against the fake harness daemon
  • Runs in bash, zsh, fish (PowerShell with Windows)

Code health

  • TS strict; any and @ts-ignore count only goes down
  • Dead code (knip), duplication, complexity limits
  • Budgets: bundle, daemon memory, startup, replay
  • Vulnerabilities, licenses, SBOM, gitleaks
  • Flaky tests quarantined with an owner + expiry
  • Schema change → version bump, migration, ADR, maintainer review

Logs

Logs are for debugging ion; the event log is product data. They never mix: chats, pins and Activity come from events; logs record what the daemon did, for you and for bug reports.

  • Where: ~/Library/Logs/ion/ on macOS, $XDG_STATE_HOME/ion/logs/ on Linux
  • Format: JSON lines, one file per component (daemon, adapter-codex, hooks…)
  • Levels: error, warn, info (default), debug, trace (raw CLI output)
  • Rotation: 10 MB × 5 per component, deleted after 14 days
  • Redacted by the same redactor as evidence, before writing
  • Bug reports: ion doctor --bundle zips recent logs, versions and config (redacted) for you to review before sharing

How it works
  • Chats is where you work. Coding and plain chats share one interface. The side panel (preview, changes, terminal, files) only appears in chats that have a project.
  • The sidebar sorts by what needs attention: Needs you, then Running (the title shimmers), then your chats by project: starred projects first and open, the rest folded, five chats each until you ask for more. Each row shows the start of the last reply and when it was last active; its menu renames or archives it. Rows have no avatars unless an ion started the chat.
  • ion is your inbox and briefing, and the place to ask anything that spans projects. It sends that work to each project’s ion and reports back.
  • Every project has exactly one ion. It holds the project’s memory and routines. A routine carries its own instructions, trigger, harness and effort, so one ion can do CI triage, dependency updates and changelogs. Chats provide the parallelism.
  • An ion’s face shows its brain. Its shape comes from the harness it runs on (spark for Claude Code, hexflower for Codex, slash for Grok Build), and its color is its own. Ions on the same harness look related but stay distinct, and switching harness keeps the color and name.
  • One place for what needs you. Project ions never notify you directly; they tell ion, which merges duplicates and decides whether to interrupt, pin, or save it for the briefing. Pins show atop ion’s chat in Ions and as “Needs you” in the Chats sidebar. It’s the same list, so resolving an item in either removes it from both.
  • A brain is harness, model and effort. One picker in the message box sets all three. Defaults apply in order: harness, project ion, routine or chat, message, and the picker shows which one is in effect. Effort maps to each harness’s own setting. Auto lets ion choose per task and say why. Every answer’s “Worked for…” line records what actually ran. The avatar’s shape follows the harness only.
  • Only ion is proactive. Project ions send it signals. When something wakes it, ion reflects on System 2 and offers at most a few suggestions, each with its evidence and a one-click action. Suggestions are optional and never count as needs; plain chat is only read if you opt in.
  • Approval happens in place. When a chat is waiting on you, a single prompt sits above its message box, so you never have to hunt for it.
  • Based on research into Grok Bot, its design post, T3 Code, and reviews of both.
